01

Foundations — Classes & Objects

Beginner

Before the "four pillars," you need the raw mechanics: what a class actually is, how Python builds an object from it, and why self shows up everywhere.

What is a class?

A class is a blueprint. It doesn't hold any data on its own — it describes what data (attributes) and behavior (methods) every object built from it will have. An object (or instance) is a concrete thing built from that blueprint, with its own copy of the data.

📐
Analogy: a class is an architect's blueprint for a house. The blueprint specifies "2 bedrooms, 1 kitchen" but you can't sleep in a blueprint. Each house actually built from it — 12 Oak St, 14 Oak St — is an object: same structure, its own address and furniture.
class Dog:
    def __init__(self, name, breed):
        self.name = name          # instance attribute
        self.breed = breed
        self.energy = 100

    def bark(self):
        return f"{self.name} says Woof!"

# Building objects from the blueprint
rex = Dog("Rex", "Labrador")
mia = Dog("Mia", "Poodle")

print(rex.bark())   # Rex says Woof!
print(mia.name)   # Mia

Why self is everywhere

self is simply the object the method was called on. When you write rex.bark(), Python translates it behind the scenes to Dog.bark(rex) — that's the whole trick. self is a parameter like any other; the name is just a very strong convention, not a keyword.

Class attributes vs. instance attributes

Instance attribute

Set on self inside __init__. Each object gets its own value.

Class attribute

Defined directly in the class body. Shared by every object unless overridden.

class Dog:
    species = "Canis familiaris"   # class attribute — shared

    def __init__(self, name):
        self.name = name                # instance attribute — unique
Common misconception
"Objects and classes are the same thing." They're not — the class is the definition, the object is the built thing. A second misconception: beginners often mutate a mutable class attribute (like a list) thinking each object gets its own copy — it doesn't, they all share the same list unless you set it in __init__.

Key takeaways

  • A class is a blueprint; an object is a concrete instance built from it
  • self refers to the specific object a method is running on
  • Instance attributes live per-object; class attributes are shared
1. What does self represent inside a method?
Correct answer: "The specific object the method is called on." self is just a parameter name by convention — rex.bark() is really Dog.bark(rex).
2. Where should you put an attribute that must be unique to every object?
Correct answer: "On self, inside __init__." Attributes set on self during initialization belong to that one instance only.
3. Two Dog objects both change a shared class attribute list. What happens?
Correct answer: "Both objects see the change." Class attributes are shared across all instances unless a method explicitly assigns a new value to self.attr.
4. What best describes the relationship between a class and an object?
Correct answer: "The class is the blueprint; the object is a built instance of it." A class can produce any number of independent objects.
02

The Four Pillars

Intermediate

Encapsulation, inheritance, polymorphism, and abstraction — the ideas that make OOP more than "functions that live inside classes."

Encapsulation

Encapsulation means bundling data with the methods that operate on it, and controlling access to that data. Python doesn't have true "private" attributes — it uses convention and name mangling instead.

class Account:
    def __init__(self, balance):
        self._balance = balance     # _single underscore: "internal use" convention
        self.__pin = "1234"       # __double underscore: name-mangled

    def withdraw(self, amount):
        if amount <= self._balance:
            self._balance -= amount
        return self._balance
🏧
Analogy: an ATM. You interact with buttons and a screen (the public method withdraw) — you never reach in and rewire the cash dispenser directly (the internal _balance). The machine controls how its own internals are touched.

Inheritance

Inheritance lets a class (the subclass) reuse and extend the behavior of another (the superclass), instead of copy-pasting code.

class Animal:
    def __init__(self, name):
        self.name = name
    def speak(self):
        return f"{self.name} makes a sound"

class Cat(Animal):              # Cat inherits from Animal
    def speak(self):             # overrides the parent method
        return f"{self.name} says Meow"

Polymorphism

Polymorphism means objects of different classes can be used through the same interface — the same method name behaves appropriately for each type.

animals = [Cat("Tom"), Dog("Rex")]
for a in animals:
    print(a.speak())     # each object answers .speak() in its own way

Abstraction

Abstraction means exposing only what's necessary and hiding implementation detail. In Python this is often done with the abc module to define a required interface subclasses must implement.

from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self): ...   # subclasses MUST implement this

Inheritance

"Is-a" relationship. A Cat is an Animal. Reuses a parent's code directly.

Composition

"Has-a" relationship. A Car has an Engine. Builds behavior by combining objects. (More in Module 3.)

Common misconception
"Private attributes in Python are truly inaccessible." They aren't — __pin is only renamed to _Account__pin (name mangling), and can still be accessed if you know that. Python trusts developers rather than enforcing hard walls.
Practical exercise

Create a Shape superclass with a method describe(), then Circle and Square subclasses that override area(). Sketch the hierarchy.

class Shape:
    def describe(self):
        return f"A shape with area {self.area():.2f}"

class Circle(Shape):
    def __init__(self, r): self.r = r
    def area(self): return 3.14159 * self.r**2

class Square(Shape):
    def __init__(self, s): self.s = s
    def area(self): return self.s**2

Key takeaways

  • Encapsulation controls access via convention (_x) and name mangling (__x)
  • Inheritance expresses "is-a" and lets subclasses reuse/override behavior
  • Polymorphism lets different objects respond to the same method call correctly
  • Abstraction defines a required interface without dictating implementation
1. What happens to self.__pin under the hood?
Correct answer: name mangling. Double-underscore attributes are renamed to include the class name, which discourages — but doesn't prevent — outside access.
2. A Cat subclass overrides speak() from Animal. This is an example of:
Correct answer: polymorphism. Calling .speak() on any animal produces the correct behavior for its actual type.
3. What does declaring an @abstractmethod in an ABC accomplish?
Correct answer: it forces subclasses to implement it — trying to instantiate a subclass that doesn't will raise a TypeError.
4. "A Car has an Engine" best describes which relationship?
Correct answer: composition — a "has-a" relationship built by holding another object, rather than inheriting from it.
03

Practical Application

Advanced

The tools you reach for once you're actually building things: dunder methods, method types, and composition over inheritance.

Dunder (magic) methods

Methods surrounded by double underscores let your objects plug into Python's built-in syntax — printing, comparison, arithmetic, and more.

class Vector:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __add__(self, other):        # enables: v1 + v2
        return Vector(self.x + other.x, self.y + other.y)

    def __repr__(self):             # enables: print(v1)
        return f"Vector({self.x}, {self.y})"

    def __eq__(self, other):        # enables: v1 == v2
        return self.x == other.x and self.y == other.y
🔌
Analogy: dunder methods are standardized power sockets. Implement __add__ and your object "plugs into" the + operator the same way an integer does — Python doesn't need a special case for your type.

Instance, class, and static methods

@classmethod

Receives cls, not self. Great for alternative constructors.

@staticmethod

Receives neither. A plain function that lives in the class's namespace for organization.

class Pizza:
    def __init__(self, toppings):
        self.toppings = toppings

    @classmethod
    def margherita(cls):                 # alternative constructor
        return cls(["tomato", "basil"])

    @staticmethod
    def is_valid_topping(name):        # doesn't need self or cls
        return name.lower() != "pineapple"

Composition over inheritance

Deep inheritance chains get brittle fast. Composition — building an object out of other objects — is often more flexible.

class Engine:
    def start(self): return "Engine running"

class Car:
    def __init__(self):
        self.engine = Engine()        # Car HAS an Engine, isn't one
    def start(self):
        return self.engine.start()
Common misconception
"You should always inherit when two classes share behavior." Prefer composition when the relationship is "has-a" rather than "is-a" — it avoids fragile, deep hierarchies where a change to a base class ripples unpredictably through every subclass.

Practical exercise

Add a __str__ and __lt__ (less-than) method to a Money class so Money objects can be printed and sorted by amount.

class Money:
    def __init__(self, amount): self.amount = amount
    def __str__(self): return f"${self.amount:.2f}"
    def __lt__(self, other): return self.amount < other.amount

Key takeaways

  • Dunder methods let your objects integrate with Python's built-in operators and functions
  • @classmethod gets cls (great for factories); @staticmethod gets neither
  • Prefer composition ("has-a") over inheritance ("is-a") when the relationship isn't truly hierarchical
1. Which dunder method makes print(obj) show something readable?
Correct answer: __repr__ / __str__. Without one, printing an object shows a default memory-address style message.
2. A @classmethod used as an alternative constructor receives:
Correct answer: cls. That's what lets it call cls(...) to build and return a new instance.
3. "A Car has an Engine" is an example of:
Correct answer: composition — Car holds an Engine object rather than inheriting from it.
4. What does @staticmethod NOT receive automatically?
Correct answer: self or cls. It behaves like a plain function that's just namespaced inside the class.

Mastery — Beyond the Basics

Expert

Multiple inheritance, the Method Resolution Order, and a first taste of design patterns.

Multiple inheritance & MRO

A class can inherit from more than one parent. Python resolves method lookup order using the C3 linearization algorithm, exposed as the Method Resolution Order (ClassName.__mro__).

class Swimmer:
    def move(self): return "swims"

class Walker:
    def move(self): return "walks"

class Duck(Swimmer, Walker):
    pass

print(Duck().move())      # "swims" — Swimmer is checked first
print(Duck.__mro__)      # (Duck, Swimmer, Walker, object)
🗺️
Analogy: MRO is a search order, like checking your own desk drawer, then your left neighbor's, then your right neighbor's, in a fixed sequence — the first drawer with the file wins, and everyone agrees on the order in advance so there's no ambiguity.

super() and cooperative inheritance

class Employee:
    def __init__(self, name):
        self.name = name

class Manager(Employee):
    def __init__(self, name, team_size):
        super().__init__(name)      # delegate to the parent's __init__
        self.team_size = team_size

A first design pattern: the Observer

Design patterns are reusable OOP solutions to recurring problems. The Observer pattern lets objects subscribe to notifications from another object — the backbone of GUI events and pub/sub systems.

class NewsPublisher:
    def __init__(self): self.subscribers = []
    def subscribe(self, fn): self.subscribers.append(fn)
    def publish(self, headline):
        for notify in self.subscribers:
            notify(headline)

publisher = NewsPublisher()
publisher.subscribe(lambda h: print(f"Alert: {h}"))
publisher.publish("OOP tutorial complete!")

Single inheritance

One parent. Predictable, simple MRO.

Multiple inheritance

Several parents. Powerful but needs care — watch for the "diamond problem," which MRO resolves deterministically.

Common misconception
"Multiple inheritance is unsafe and unpredictable in Python." It's actually deterministic — the MRO gives a single, well-defined lookup order — but it's still good practice to keep hierarchies shallow and prefer mixins with narrow, focused responsibilities.

Practical exercise

Create Flyer and Swimmer mixins, then a Duck(Flyer, Swimmer) class that uses super().__init__() cooperatively for setup.

class Flyer:
    def fly(self): return "flying"

class Swimmer:
    def swim(self): return "swimming"

class Duck(Flyer, Swimmer):
    def show_skills(self):
        return f"{self.fly()} and {self.swim()}"

Key takeaways

  • MRO gives a deterministic order for method lookup in multiple inheritance
  • super() delegates to the next class in the MRO, not just "the parent"
  • Design patterns like Observer are OOP principles applied to recurring real problems
1. What does Duck.__mro__ give you?
Correct answer: it's the Method Resolution Order — the exact sequence of classes checked for an attribute or method.
2. In class Duck(Swimmer, Walker), which parent is checked first for a shared method name?
Correct answer: Swimmer — parent order in the class definition determines MRO priority, left to right.
3. What does super().__init__(name) do inside Manager.__init__?
Correct answer: it delegates to the next class in the MRO, letting Manager reuse Employee's setup logic.
4. What problem does the Observer pattern primarily solve?
Correct answer: it lets a subject notify a list of subscribers automatically — the basis for events and pub/sub systems.

Final Practical Challenge

Bring every pillar together in one design.

Challenge

Design a small library system: an abstract Media base class (ABC) with describe(), subclasses Book and DVD that override it (polymorphism), a Library class that has a list of Media (composition), private tracking of checked-out items (encapsulation via _checked_out), and a __len__ dunder method so len(library) returns the item count.

from abc import ABC, abstractmethod

class Media(ABC):
    def __init__(self, title): self.title = title
    @abstractmethod
    def describe(self): ...

class Book(Media):
    def describe(self): return f"Book: {self.title}"

class DVD(Media):
    def describe(self): return f"DVD: {self.title}"

class Library:
    def __init__(self):
        self._items = []
        self._checked_out = set()
    def add(self, media): self._items.append(media)
    def __len__(self): return len(self._items)
